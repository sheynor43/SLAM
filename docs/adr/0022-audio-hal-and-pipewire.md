# ADR-0022: Интерфейс HAL аудио, позиция воспроизведения и бэкенд PipeWire

- Статус: Принято
- Дата: 2026-10-10

## Контекст
ADR-0004 определил набор бэкендов (WASAPI, PipeWire, ALSA), но не интерфейс HAL. Для #9 нужны: перечисление устройств, открытие выходного потока с частотой и размером буфера, колбэк без аллокаций и блокировок, сообщаемая задержка и позиция воспроизведения для update-потока (игровое время, ARCHITECTURE §4). Для PipeWire нужно выбрать биндинги.

## Решение
- **Формат.** Колбэк всегда получает `f32` с чередованием каналов (interleaved). Частота и число каналов задаются в `StreamConfig`, размер буфера — желаемое число кадров на колбэк (для PipeWire — квантум). Фактический размер буфера может меняться от колбэка к колбэку: колбэк обязан обрабатывать любое число кадров.
- **Колбэк** — трейт `AudioCallback: Send + 'static` с методом `process(&mut self, out, &CallbackInfo)`. HAL владеет им как `Box<dyn AudioCallback>`: один виртуальный вызов на буфер. `CallbackInfo` содержит номер первого кадра буфера в потоке, таймстемп и задержку до выхода. По ним микшер ставит звук на точный кадр.
- **Позиция для update** — `AudioPosition`: seqlock на атомиках, один писатель (аудиопоток). Без блокировок для обеих сторон. После каждого буфера публикуется четвёрка:
  - номер кадра `frame`;
  - таймстемп `timestamp_ns`;
  - задержка `latency_ns` — время от `timestamp_ns` до выхода кадра `frame` из устройства;
  - частота.

  Кадр на выходе в момент `t` равен `frame + (t − timestamp_ns − latency_ns) · rate / 1e9`. Формула общая для всех бэкендов. Экстраполяцию и сглаживание делает потребитель (аудиоклок), а не бэкенд.
- **Часы.** `timestamp_ns` идёт в базе `CLOCK_MONOTONIC` на Linux (как часы движка) и QPC на Windows. `slam-audio` не зависит от `slam-engine`, поэтому совпадение баз — контракт бэкенда.
- **API.** Бэкенд выбирается значением `Backend`, функции `devices(backend)` и `open_output(backend, config, callback)`. Возвращается `OutputStream`: фактический формат, `Arc<AudioPosition>`. При `Drop` поток закрывается.
- **PipeWire** через крейт `pipewire` (pipewire-rs, MIT, freedesktop.org) с фичей `v1_0_0`:
  - Квантум задаётся свойством `node.latency = <кадры>/<частота>`. Целевое устройство — `target.object` (имя узла).
  - Флаги потока — `RT_PROCESS | AUTOCONNECT | MAP_BUFFERS`. Колбэк выполняется в data-потоке PipeWire, приоритет реального времени ему выдаёт сам PipeWire (module-rt / rtkit). Свой аудиопоток не нужен.
  - Цикл PipeWire (`MainLoop`) живёт в отдельном потоке `slam-audio-pw`. Команды к нему (остановка) идут через `pipewire::channel`.
  - Задержка = `pw_time.buffered / rate_потока + pw_time.delay · rate_графа`, от `pw_time.now`. Число кадров на колбэк — `pw_buffer.requested`.
  - Устройства — глобальные объекты реестра с `media.class = Audio/Sink`.

## Последствия
- Колбэк не делает системных вызовов, не аллоцирует и не берёт блокировок. Поведение самого PipeWire внутри `dequeue`/`queue` — его ответственность (заявлено RT-safe). Проверка: тест с реальным потоком (аллокации Rust) и ручной `strace`.
- Задержку сообщает PipeWire. Её точность проверяется замером клик → звук (#11).
- Минимальная поддерживаемая версия libpipewire — 1.0 (Ubuntu 24.04).
- Сборка на Linux требует `libpipewire-0.3-dev` и `libclang` (bindgen).
- Устройство по умолчанию в списке пока не отмечается: для этого нужны метаданные `default`.

## Отвергнутые варианты
- **cpal** как основа: нет управления квантумом PipeWire и режимами WASAPI, а задержка сообщается только приближённо. ADR-0004 допускал его лишь как временный бэкенд.
- **Голые биндинги `pipewire-sys`:** тот же результат с большим объёмом `unsafe`. Rust-обёртка `pipewire` в process-пути не аллоцирует.
- **`pw_thread_loop` и свой поток с колбэком без `RT_PROCESS`:** лишний переход между потоками и блокировка цикла на каждом буфере.
- **Позиция как один атомарный счётчик кадров:** без таймстемпа и задержки update не может экстраполировать время между колбэками.
