# ADR-0018: GL-контекст в потоке draw, поверхность через трейт, хуки потока draw

- Статус: Принято
- Дата: 2026-10-08

## Контекст
По ADR-0002 окно и события живут на главном потоке, а кадр собирает и показывает поток draw. Бэкенд OpenGL 3.3 (ADR-0003) работает с контекстом SDL3. SDL3 помечает `SDL_GL_MakeCurrent`, `SDL_GL_GetProcAddress`, `SDL_GL_SwapWindow` и `SDL_GL_DestroyContext` как «только главный поток». При этом в коде видео SDL 3.4 проверок главного потока нет. На Wayland swap ждёт кадр через отдельную очередь событий (`gles_swap_frame_event_queue`, потокобезопасный `wl_display_prepare_read_queue`), а при swap interval 0 сводится к `eglSwapBuffers` и flush. На X11 SDL вызывает `XInitThreads`. На Windows `SwapBuffers` работает из любого потока, пока контекст текущий только в нём. По ARCHITECTURE §3 `slam-render` не зависит от `slam-input`, и наоборот. Контекст GL должен стать текущим в потоке draw до загрузки указателей функций (на Windows они привязаны к контексту), а перед разрушением освободиться.

## Решение
- **Контекст в потоке draw.** `slam-input` создаёт окно с флагом OpenGL и контекст 3.3 core на главном потоке, ставит swap interval 0 и освобождает контекст. Поток draw делает его текущим, загружает функции GL, рисует и вызывает swap. Это осознанное отступление от пометки SDL. Оно проверяется на Linux (Wayland, X11) и Windows. Если при обновлении SDL поведение изменится, контекст переедет на главный поток.
- **Поверхность через трейт.** `slam-render` задаёт трейт `GlSurface`: `make_current`, `release_current`, `get_proc_address`, `swap_buffers`, размер в пикселях. `slam-input` предоставляет `GlContext`, а трейт для него реализует обёртка `slam-engine::gl::SdlGlSurface`: `slam-engine` зависит от обоих крейтов. Размер окна поток draw читает из атомиков, которые обновляет главный поток по событиям изменения размера. Оконные функции SDL из потока draw не вызываются.
- **Хуки потока draw.** У трейта `slam-engine::Draw` появляются `start` и `stop` (по умолчанию пустые). Они выполняются в потоке draw до первого кадра и после последнего. В `start` устройство делает контекст текущим и загружает GL, в `stop` освобождает контекст.
- **Время жизни.** `GlContext` помнит поток, в котором он текущий: сделать его текущим во втором потоке нельзя, а уничтожение из чужого потока оставляет контекст утёкшим, а не разрушенным под тем потоком. `GlContext` держит общий с окном счётчик: если окно уничтожается, пока контекст жив, окно и SDL намеренно утекают. Правильный порядок: остановить движок, затем уничтожить контекст и окно. Устройство снимает отладочный колбэк GL до освобождения контекста.
- **Без глобального реестра объектов на кадре.** По умолчанию SDL проверяет каждый указатель окна в глобальной таблице под rwlock, в том числе в `SDL_GL_SwapWindow`. `slam-input` ставит подсказку `SDL_INVALID_PARAM_CHECKS=1` (только быстрые проверки) перед каждой инициализацией SDL.

## Последствия
- Present происходит в потоке draw без участия главного потока и не добавляет задержку пересылки кадра.
- Мы полагаемся на недокументированное поведение SDL: при обновлении SDL нужно проверить swap и make current из потока draw на Wayland, X11 и Windows.
- Изменение размера окна на Wayland применяется к буферу из главного потока, пока поток draw может делать swap. Mesa применяет новый размер при следующем захвате буфера; гонку нужно отслеживать на практике. Swap читает статус показа окна (`shell_surface_status`) без синхронизации: в худшем случае пропускается кадр-другой при показе или скрытии.
- X11: swap (`X11_HandlePresent`) читает и пишет поля синхронизации изменения размера (`_NET_WM_SYNC_REQUEST`), которые главный поток пишет при обработке событий. Возможен потерянный или повторный ответ оконному менеджеру: окно может «замёрзнуть» посреди изменения размера до следующего запроса. Полное исправление — swap на главном потоке; пока проверяется вручную.
- Подсказка `SDL_INVALID_PARAM_CHECKS=1` отключает проверку объектов во всём SDL: неверный указатель приведёт к падению, а не к ошибке. Наши указатели верны по построению.
- `Draw::start` не может вернуть ошибку: сбой создания устройства — паника в потоке draw, видная только при остановке движка.
- Будущие бэкенды (D3D11, Vulkan) получают свою поверхность тем же способом: свой трейт в `slam-render`, реализация в `slam-input`, склейка в `slam-engine`.

## Отвергнутые варианты
- Swap на главном потоке по сигналу от draw: лишнее пробуждение и пересылка кадра между потоками, главный поток занят ожиданием событий ОС.
- Весь рендер на главном потоке: противоречит ADR-0002 (события ОС не должны ждать кадра).
- Свой EGL/GLX/WGL в обход SDL: три реализации ради того, что SDL уже делает потокобезопасно.
- Фабрика состояния draw (`FnOnce() -> D` на потоке draw) вместо хуков: меняет API `Engine::spawn` сильнее, а освобождение контекста при остановке всё равно требует хука.
