# ADR-0075: Приоритет GL-контекста на GPU

- Статус: Принято
- Дата: 2026-10-29

## Контекст
Параллельная нагрузка на GPU (запись экрана в OBS) задерживает кадры SLAM до ~2,5 мс: задания OBS и наши стоят в одной очереди `gfx_0.0.0` и не вытесняют друг друга (разбор — `docs/perf/2026-10-10-present-stalls.md`, задача #163). Композитор niri создаёт контекст высокого приоритета (`EGL_IMG_context_priority`), его задания идут в отдельную очередь `gfx_0.1.0`.

Что выяснилось на RX 6700 XT, Mesa 26.2.5, ядро 7.3 (bench на 1000 Гц, параллельно второй процесс с тяжёлыми кадрами):
- SDL 3.4 позволяет добавить атрибуты EGL-контекста через `SDL_EGL_SetAttributeCallbacks`: свой EGL писать не нужно. Массив атрибутов колбэк выделяет через `SDL_malloc`, SDL его освобождает.
- На X11 SDL по умолчанию создаёт контекст через GLX, атрибута там нет. С хинтом `SDL_VIDEO_FORCE_EGL` контекст создаётся через EGL; FPS и p99 фреймтайма без нагрузки те же, что у GLX (13,5–13,6 тыс. FPS, p99 ~300 мкс).
- amdgpu (как и i915) даёт приоритет выше обычного только процессу с `CAP_SYS_NICE` (или мастеру DRM). Без права контекст с запросом HIGH создаётся без ошибки, и `eglQueryContext` возвращает HIGH, но задержки как без запроса (871–914 кадров после перерасхода за 4 с против 911–934). С правом на копии бинаря (`setcap cap_sys_nice+ep`) — 168–199 против 815–870, p99 фреймтайма 1,56–1,63 мс против 1,95–1,97 мс. То есть ответ драйвера о выданном приоритете на amdgpu недостоверен.

## Решение
- **Запрос.** `GlContext::create` (`slam-input`) ставит колбэк атрибутов контекста. Колбэк добавляет `EGL_CONTEXT_PRIORITY_LEVEL_IMG = EGL_CONTEXT_PRIORITY_HIGH_IMG`, если дисплей объявляет `EGL_IMG_context_priority`; иначе пустой список. После создания колбэк снимается. На Linux перед `SDL_Init` ставится хинт `SDL_VIDEO_FORCE_EGL=1`, чтобы X11 тоже шёл через EGL. На Windows (WGL) колбэк не вызывается, поведение прежнее; аналог для D3D11 — отдельная задача.
- **Откат.** Если контекст с атрибутом не создался, он создаётся ещё раз без колбэка, ошибка первой попытки сохраняется.
- **Итог** — `GlContext::priority()` → `PriorityOutcome`:
  - `Unsupported` — не EGL или нет расширения;
  - `Granted(level)` — уровень по `eglQueryContext`, и у процесса есть право на него;
  - `NoPermission` — драйвер ответил HIGH, но это драйвер Mesa на Linux (`Mesa` в `GL_VERSION`), а у процесса нет `CAP_SYS_NICE` (бит в `CapEff` из `/proc/self/status`): на amdgpu, i915 и xe задания идут с обычным приоритетом. Ответу остальных драйверов верим;
  - `Refused(error)` — создание с добавленным атрибутом не удалось, работает обычный контекст.
- **Отчёт.** Оболочка и `play` пишут итог в лог (`info` для `Granted`, `warn` с подсказкой про `setcap` для `NoPermission` и `Refused`). `bench` печатает его в отчёте, флаг `--no-gpu-priority` отключает запрос для сравнения. Настройки в интерфейсе нет: запрос без права безвреден.
- **Право** пользователь выдаёт сам: `sudo setcap cap_sys_nice+ep <путь к slam>` для распакованного бинаря. Внутри AppImage право не действует (FUSE монтируется с `nosuid`): AppImage распаковывают (`--appimage-extract`) и выдают право `squashfs-root/usr/bin/slam`. Инструкция — в заметках о выпуске.

## Последствия
- При записи экрана и прочей нагрузке на GPU кадры SLAM ждут меньше, но только с `CAP_SYS_NICE`. Часть задержек остаётся: с OBS на 8000 Гц FPS на 20 % ниже, чем без него (замеры — `docs/perf/2026-10-29-gpu-priority.md`).
- После пересборки или обновления бинаря право теряется (запись в файл сбрасывает file capabilities), его надо выдать снова.
- `CAP_SYS_NICE` разрешает процессу и повышать приоритет своих потоков на CPU; SLAM этим пока не пользуется.
- X11 теперь всегда идёт через EGL. Если найдётся система, где EGL на X11 хуже GLX, — новый ADR.
- NVIDIA (проприетарный драйвер) и Intel не проверены.

## Отвергнутые варианты
- **Собственное создание EGL-контекста под окно SDL.** Колбэк SDL делает то же без своего кода для Wayland и X11.
- **Доверять `eglQueryContext`.** На amdgpu без права он сообщает HIGH, хотя ядро его не дало.
- **Запрашивать HIGH только при наличии права.** Права проверяются по-разному в разных драйверах; запрос без права ничего не ломает, а на драйвере без такой проверки поможет.
- **Повышать права установщиком или setuid-обёрткой.** Выдача прав — решение пользователя; AppImage их всё равно не переносит.
