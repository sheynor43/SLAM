# ADR-0024: Основной бэкенд рендера: OpenGL на Linux, D3D11 на Windows

- Статус: Принято
- Дата: 2026-10-10
- Уточняет ADR-0003 (порядок бэкендов не меняется, снимаются оговорки «по бенчмарку»)

## Контекст
ADR-0003 оставил выбор основного бэкенда на Windows (D3D11) и необходимость Vulkan на Linux до бенчмарка M0. Бенчмарк-сцена M0 ([отчёт](../perf/2026-10-10-bench-scene.md)) есть только для OpenGL 3.3 на Linux; бэкендов D3D11 и Vulkan нет, замеров на Windows нет. Сравнить бэкенды напрямую нельзя.

Что показал замер (Ryzen 7 5700X, RX 6700 XT, Mesa 26.2, niri):
- Свой код в бюджете: сборка и отрисовка 500 спрайтов одним draw call — ~30 мкс (p50). Без лимита — ~10 300 FPS на X11 и 8 100–10 000 на Wayland (цель ≥ 8000). p99 опоздания лимитера ≤ 1 мкс (цель < 50).
- Узкое место — `present` (swap): медиана 37–74 мкс даже на пустом кадре и задержки по ~1.5 мс примерно 45 раз в секунду на Wayland и X11. Из-за них p99 фреймтайма 0.7–1 мс, и 5–13% кадров под лимитером 1000–8000 Гц пропускают дедлайн. Источник — WSI Mesa или композитор; причина не выяснена.

На Windows у OpenGL в оконном и borderless-режиме кадр идёт через композитор DWM без управления моделью показа (ADR-0003). У D3D11 через DXGI есть flip-model swapchain, показ с разрывом (`DXGI_PRESENT_ALLOW_TEARING`) и waitable swapchain для ограничения очереди кадров. osu-framework на Windows тоже пробует D3D11 первым, OpenGL — запасным (`GameHost.GetPreferredRenderersForCurrentPlatform`).

## Решение
- **Linux: основной бэкенд — OpenGL 3.3.** Vulkan не начинается. Сначала исследуются задержки `present` в OpenGL: число буферов swapchain, поведение EGL/GLX при swap interval 0, полноэкранный режим (direct scanout) против оконного, другой композитор ([#28](https://github.com/sheynor43/SLAM/issues/28)).
- **Условие для Vulkan на Linux:** выбросы `present` остаются после этого исследования, а минимальный прототип Vulkan с `MAILBOX` или `IMMEDIATE` на той же машине и сцене (`slam-app bench`) их убирает или заметно снижает p99 фреймтайма. Тогда Vulkan-бэкенд делается вне очереди «Позже», отдельным ADR.
- **Windows: основной бэкенд — D3D11** (flip-model, tearing при отключённой вертикальной синхронизации, waitable swapchain). OpenGL 3.3 — фолбэк, если D3D11 не создаётся. Бэкенд D3D11 — в этапе M2 ([#29](https://github.com/sheynor43/SLAM/issues/29)). До него на Windows работает OpenGL.
- Решение по Windows принимается без замеров. Первый замер `slam-app bench` на Windows (D3D11 и OpenGL на одной машине) — часть готовности бэкенда D3D11. Если D3D11 там окажется хуже OpenGL по фреймтайму или задержке, нужен новый ADR.

## Последствия
- HAL рендера не меняется. Шейдеры для D3D11 транслируются `naga` в HLSL при сборке (ADR-0019). Координаты HAL уже как в D3D, второй вариант вершинного шейдера не нужен.
- Поверхность D3D11 потребует своего трейта или реализации поверхности (как `GlSurface`, ADR-0018), с HWND от SDL.
- Пока на Linux задержки `present` не разобраны, p99 фреймтайма на Linux ~0.7–1 мс — это известное ограничение, не регрессия.
- Цифры для Windows — долг до M2.

## Отвергнутые варианты
- **Сделать D3D11 и Vulkan в M0 ради прямого сравнения**: два бэкенда до первого играбельного геймплея. Наш код в бюджете, вопрос только в показе кадра — его дешевле сначала исследовать в OpenGL.
- **Vulkan на Linux сразу**: причина задержек `present` не выяснена. Если она в композиторе, Vulkan её не уберёт, а поддерживать два бэкенда на одной платформе дорого.
- **OpenGL как основной на Windows**: нет управления моделью показа и лишняя задержка композитора в окне (ADR-0003).
- **Отложить решение до замеров на Windows**: оставляет M0 открытым без даты. Риск ошибки ограничен: OpenGL остаётся фолбэком, при плохих цифрах пишется новый ADR.
