# ADR-0094: Блокировка клавиши Windows (и сочетаний рабочего стола на Linux) во время игры

- Статус: Принято
- Дата: 2026-11-04
- Дополняет [ADR-0048](0048-live-settings.md): новый получатель настройки, который действует сразу

## Контекст
Игроки на Windows случайно нажимают клавишу Windows посреди карты. Открывается меню «Пуск», окно теряет фокус.

В лазере есть настройка `GameplayDisableWinKey` («Disable Windows key during gameplay»):
- по умолчанию включена, видна только на Windows (`InputSettings`);
- `GameplayWinKeyBlocker` ставит глобальный низкоуровневый хук клавиатуры `WH_KEYBOARD_LL`, только пока окно активно, настройка включена и игрок в состоянии `LocalUserPlayingState.Playing`. Пауза, перерыв, провал, прохождение и просмотр реплея в это состояние не входят;
- хук съедает нажатия и отпускания левой и правой клавиш Windows (`VK_LWIN`, `VK_RWIN`). Остальные клавиши проходят дальше (`CallNextHookEx`).

## Решение
- **Настройка.** `[gameplay] disable_win_key` в `slam.toml`, по умолчанию `true` на всех ОС. Строка в разделе игры:
  - на Windows — «Отключать клавишу Windows во время игры»;
  - на Linux — «Отключать системные сочетания клавиш во время игры»;
  - на других ОС скрыта.
- **Хук в `slam-input`.** Хук ставит поток окна, потому что низкоуровневый хук выполняет цикл сообщений того потока, который его поставил, а у потока окна этот цикл крутит SDL (`SDL_WaitEvent`). Хук стоит, пока выполнены оба условия: есть пожелание и у окна фокус ввода. Фокус окно отслеживает само по событиям SDL. Хук съедает только `VK_LWIN` и `VK_RWIN` в сообщениях от `WM_KEYDOWN` до `WM_SYSKEYUP`, остальное передаёт дальше.
- **Linux: захват клавиатуры SDL.** На KDE клавиша Meta открывает меню запуска, на GNOME — обзор окон, поэтому мешает и здесь. Заблокировать одну клавишу на Linux нельзя. При тех же условиях окно включает `SDL_SetWindowKeyboardGrab`: на Wayland SDL просит композитор не обрабатывать свои сочетания (`keyboard-shortcuts-inhibit`), на X11 захватывает клавиатуру. Пока идёт игра, не работают все сочетания рабочего стола: Super, Alt+Tab, переключение рабочих столов. В полноэкранном режиме SDL сам оставляет Alt+Tab, чтобы из игры можно было выйти. Решение пользователя: по умолчанию включено и на Linux. На других ОС пожелание просто хранится.
- **Пожелание.** Его передаёт ручка `WinKeyBlock` на атомике, без блокировок, как `CursorVisibility`. Окно применяет пожелание перед ожиданием следующего события.
- **Когда блокировать.** Поток update в каждом тике игры просит блокировку, если настройка включена, состояние `Waiting` или `Playing` и сейчас не перерыв (`is_break_time` — порт `BreakTracker`, включая время до первого объекта). В паузе, при ожидании клика после паузы, при провале, прохождении и на результатах клавиша работает. Конец игры снимает пожелание.
- **Настройка действует сразу**, а не со следующей карты: её можно переключить в паузе.

## Последствия
- Клавиша Windows не открывает «Пуск» посреди карты. В паузе и в меню она работает как обычно.
- Окно не будится ради пожелания, потому что будильник — это блокировка и системный вызов в тике update. Хук ставится или снимается после ближайшего события окна. Во время игры события идут постоянно: движение мыши, нажатия. Поэтому задержка на практике меньше миллисекунды.
- Хук глобальный: пока он стоит, клавиша Windows не работает во всей системе, но только пока у окна фокус. Если поток окна завис, Windows пропускает хук по таймауту (`LowLevelHooksTimeout`).
- Хук работает, только пока поток окна ждёт события. Пока окно занято, например сменой видеорежима, системный ввод может подтормаживать. Каждое нажатие при стоящем хуке проходит лишний круг через поток окна. У лазера то же самое: его хук стоит на потоке ввода. Задержку стоит замерить на Windows при ручной проверке.
- Выход из цикла окна сразу снимает хук. Иначе после закрытия окна посреди карты глобальный хук без цикла сообщений тормозил бы клавиатуру всей системы, пока программа завершается.
- Отдельная команда `slam play` клавишу не блокирует: это инструмент разработчика.
- Если захват или хук не удались, ошибка пишется в лог один раз. Новая попытка — только когда меняется пожелание или фокус. На Wayland без протокола `keyboard-shortcuts-inhibit` захват не работает.
- **Под Wayland-композитором через X11 (Xwayland) блокировка не действует.** Захват X11 работает только внутри X-сервера, а сочетания обрабатывает сам композитор. На niri это проверено: через X11 сочетания работают, с `SDL_VIDEO_DRIVER=wayland` блокируются. Сейчас SDL на niri по умолчанию выбирает X11, поэтому блокировка там заработает, когда по умолчанию будет выбираться Wayland (отдельная задача). Строка лога `system shortcuts block` уровня info показывает, включён ли захват и какой драйвер работает.
- На X11 SDL не проверяет результат `XGrabKeyboard` и в оконном режиме сам отпускает захват, когда курсор уходит из окна. Захват возвращается при следующем получении фокуса. В полноэкранном режиме и в режиме относительной мыши этого не бывает.
- На GNOME при первом захвате композитор спрашивает разрешение. На niri через Wayland проверено, сочетания возвращает Mod+Escape. На KDE не проверено.
- Хук проверить можно только на Windows. В CI проходят сборка, clippy под `x86_64-pc-windows-gnu` и тесты чистой логики. Ручная проверка — вместе с остальными проверками Windows в конце M2.

## Отвергнутые варианты
- **Захват клавиатуры SDL на Windows.** Он перехватывает и Alt+Tab, и другие системные сочетания, а нужна только клавиша Windows. В лазере его нет. На Linux другого способа нет, поэтому там он используется.
- **На Linux по умолчанию выключено.** В лазере на Linux такой настройки нет, а захват сильнее, чем блокировка одной клавиши. Пользователь решил включить по умолчанию: в паузе и меню сочетания работают.
- **Хук на отдельном потоке со своим циклом сообщений.** Лишний поток. У потока окна цикл сообщений уже есть.
- **Будить окно при каждой смене пожелания.** Это блокировка и `SDL_PushEvent` в тике update. Выигрыш — доли миллисекунды в момент паузы или перерыва.
