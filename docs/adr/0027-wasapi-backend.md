# ADR-0027: Бэкенд WASAPI

- Статус: Принято
- Дата: 2026-10-10
- Уточняет [ADR-0004](0004-audio-hal.md) (режимы WASAPI) и [ADR-0022](0022-audio-hal-and-pipewire.md) (интерфейс HAL: выбор режима, фактический режим и период)

## Контекст
ADR-0004 требует для Windows три режима WASAPI: shared, shared low-latency (`IAudioClient3`) и exclusive, с MMCSS «Pro Audio» для аудиопотока. ADR-0022 описал HAL на примере PipeWire, но не сказал, как выбирать режим, что делать при неподдерживаемом режиме и как WASAPI сообщает задержку. Нужны биндинги к COM-интерфейсам: в `windows-sys`, который уже используется движком, обёрток COM нет.

## Решение
- **Биндинги** — крейт `windows` (Microsoft, MIT/Apache-2.0) с COM-интерфейсами `IMMDeviceEnumerator`, `IAudioClient`/`IAudioClient3`, `IAudioRenderClient`, `IAudioClock`. Подключается только под Windows.
- **Режим — часть бэкенда:** `Backend::Wasapi(WasapiMode::{Shared, LowLatency, Exclusive})`. Неподдерживаемый режим откатывается к менее требовательному: Exclusive → LowLatency → Shared. Фактический режим отдаёт `OutputStream::backend()`, полученный период — `OutputStream::config().buffer_frames`. Имена бэкендов для настроек и командной строки — `Backend::name()` / `Backend::from_name()`: `pipewire`, `wasapi-shared`, `wasapi-low-latency`, `wasapi-exclusive`.
- **Режимы:**
  - *Shared* — `IAudioClient::Initialize` с периодом движка по умолчанию (~10 мс), `AUTOCONVERTPCM | SRC_DEFAULT_QUALITY`: системный микшер сам приводит частоту и каналы. `buffer_frames` игнорируется.
  - *LowLatency* — `IAudioClient3::InitializeSharedAudioStream` с периодом из `GetSharedModeEnginePeriod`: запрошенный `buffer_frames`, округлённый вверх до кратного фундаментальному и зажатый в [min, max] драйвера. Конвертации здесь нет, поэтому частота и каналы потока должны совпадать с mix format, иначе — откат на Shared.
  - *Exclusive* — `IAudioClient::Initialize(EXCLUSIVE)`, период — запрошенный `buffer_frames`, но не меньше минимального периода устройства. Формат устройства перебирается через `IsFormatSupported`: f32 → i32 → i24 в 32-битном контейнере → упакованный i24 → i16. Колбэк всегда пишет `f32`; для целочисленных форматов бэкенд конвертирует сам, через буфер, выделенный при открытии. На `AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED` — повтор на новом клиенте с периодом, равным выровненному размеру буфера.
- **Поток.** У каждого потока свой поток ОС `slam-audio-wasapi` в многопоточном апартаменте COM, зарегистрированный в MMCSS как «Pro Audio» (если MMCSS недоступен — предупреждение в лог, поток работает дальше). Режим event-driven: поток ждёт событие буфера (`WaitForSingleObject`, таймаут 100 мс для проверки остановки и пропажи устройства) и заполняет один буфер. Перед `Start` буфер заполняется тишиной.
- **Сколько писать.** В exclusive — весь буфер на каждое событие. В shared-режимах — доливать до двух периодов в очереди (один играет, второй готов): `min(свободно, 2·период − padding)`. Больше двух периодов только добавляет задержку.
- **Задержка и часы.** Перед каждым буфером `IAudioClock::GetPosition` даёт позицию устройства и QPC момента этой позиции. Задержка первого кадра буфера = `(записано − сыграно) / частота`, где `сыграно = позиция · частота / GetFrequency()`, таймстемп = QPC (в единицах 100 нс) × 100. Часы движка на Windows — QPC в наносекундах, базы совпадают с точностью до 100 нс (контракт ADR-0022).
- **Устройства** — активные render-эндпоинты; id — строка `IMMDevice::GetId`, имя — `PKEY_Device_FriendlyName`. Устройство по умолчанию — `eRender`/`eConsole`. Перечисление идёт в отдельном коротком потоке, чтобы не трогать COM-апартамент вызывающего потока (например, окна SDL).
- **Ошибки.** `AUDCLNT_E_DEVICE_INVALIDATED` и любые ошибки вне `GetBuffer` останавливают цикл и ставят `StreamCounters::failed`. Прочие ошибки `GetBuffer` и невыровненный буфер `f32` считаются как `missed_buffers`. Паника колбэка завершает только поток бэкенда и тоже ставит `failed`. Если поток не настроил устройство за 5 с (зависший драйвер), `open_output` возвращает ошибку, не дожидаясь его: поток отсоединяется и завершается сам, когда настройка вернётся.
- **SDL3 на Windows (MSVC)** собирается из исходников и линкуется статически, как на Linux: так job на `windows-latest` собирает весь workspace без системного SDL3. Кросс-проверка `x86_64-pc-windows-gnu` с Linux по-прежнему ищет SDL3 через pkg-config: компилятора C для этой цели нет.

## Последствия
- Колбэк по-прежнему не делает системных вызовов, не аллоцирует и не блокируется. Вызовы WASAPI (`GetCurrentPadding`, `GetBuffer`, `GetPosition`, `ReleaseBuffer`) делает цикл бэкенда, как PipeWire делает `dequeue`/`queue`.
- Задержку сообщает драйвер через `IAudioClock`. Её точность, как и для PipeWire, проверяется замером клик → звук; на Windows его ещё не было. Основная машина разработки — Linux: бэкенд проверен сборкой, юнит-тестами чистой логики и тестами с реальным устройством, которые на раннерах CI пропускаются (там нет звукового устройства). Ручная проверка на Windows — отдельная задача.
- В exclusive звук других приложений на устройстве не слышен (ADR-0004); пользователя предупреждают в настройках.
- LowLatency на устройстве, где драйвер не даёт малых периодов (min = max = период по умолчанию), работает как Shared с периодом ~10 мс.
- В shared-режимах частота и каналы потока могут отличаться от mix format только в Shared (конвертирует система, добавляя задержку ресемплера). Если микшер и хитсаунды готовятся под mix format, LowLatency доступен без отката.
- `Backend::available()` на Windows: LowLatency, Exclusive, Shared — первым идёт режим, который не забирает устройство у других программ.

## Отвергнутые варианты
- **cpal / wasapi-rs как основа.** cpal не даёт `IAudioClient3` и exclusive с выбором формата, задержку сообщает приближённо (как и в ADR-0022). Крейт `wasapi` добавляет слой поверх тех же интерфейсов, но не убирает `unsafe` вокруг буфера и формата.
- **`windows-sys` с ручными vtable COM.** Тот же результат с гораздо большим объёмом `unsafe`.
- **Режим в `StreamConfig`.** Режим имеет смысл только для WASAPI; как часть `Backend` он виден в настройках одним списком и сразу сообщает фактический результат отката.
- **Ошибка вместо отката при неподдерживаемом режиме.** Пользователь получил бы тишину из-за занятого устройства или формата; откат с записью в лог и фактическим режимом в `OutputStream` полезнее.
- **Заполнять весь свободный буфер в shared-режимах.** Буфер shared-потока обычно больше двух периодов, и задержка выросла бы без пользы.
- **Опрос (`Sleep` по таймеру) вместо событий.** Больше задержка и джиттер, чем у event-driven режима; exclusive event-driven — рекомендованный Microsoft путь для малых периодов.
