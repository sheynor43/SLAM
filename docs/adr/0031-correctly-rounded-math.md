# ADR-0031: Трансцендентные функции геймплея с правильным округлением (`pxfm`)

- Статус: Принято
- Дата: 2026-10-11

## Контекст
Правила геймплея используют `sin`, `cos`, `atan2`, `acos` (геометрия дуг слайдеров), `pow` (счёт) и `atan2f` (угол спиннера). Методы `f64::sin` и др. в Rust вызывают системную libm: glibc, UCRT на Windows, libm Apple. Их последние биты различаются между платформами, а на Windows и в glibc x86_64 — ещё и между процессорами с FMA и без. Это нарушает принцип детерминизма (ARCHITECTURE §2): один реплей может дать разный результат на разных ОС.

Лазер сам не детерминирован между платформами. .NET (`Math.Sin`, `MathF.Atan2` и др.) вызывает C-рантайм платформы — и в .NET 8–10, и в `main` (`floatdouble.cpp`). Документация .NET прямо говорит, что результат зависит от ОС и архитектуры. Ни одна из трёх системных libm не даёт правильного округления для этих функций в `double`. Ошибки по замерам Gladman–Innocente–Mather–Zimmermann (2025):
- glibc — около 0,52 ULP;
- UCRT — 0,75–0,9 ULP, а `pow` — до 91 ULP;
- Apple — 0,75–1,06 ULP.

`atan2f` с правильным округлением — только в glibc ≥ 2.41 (CORE-MATH).

Замер на 737 756 уникальных вызовах из всех тестов `slam-osu`. Входы сняты на glibc 2.44, эталон — MPFR.

| Функция | glibc ≠ правильному | `libm` ≠ правильному | `pxfm` ≠ правильному |
|---|---|---|---|
| sin / cos | 0,13–0,16 % | 2,8 % | 0 |
| atan2 | 0,09 % | 18 % | 0 |
| acos | 0,4 % | 0 | 0 |
| pow | 0,08 % | 8 % | 0 |
| atan2f | 0 | 16 % | 0 |

Эталонные тесты лазера (пути, вложенные объекты, стэкинг, моды, счёт, здоровье) и корпус реплеев проходят со всеми тремя вариантами. Последние биты `double` исчезают при приведении к `f32` и при округлении счёта. Выбор поэтому определяет прежде всего детерминизм между платформами, а не паритет с лазером на наших данных.

## Решение
1. Все трансцендентные функции правил вызываются только через модуль `slam_osu::math`. Он реализован на крейте `pxfm` (BSD-3-Clause OR Apache-2.0, чистый Rust): `f_sin`, `f_cos`, `f_atan2`, `f_acos`, `f_pow`, `f_atan2f`. Версия зафиксирована точно (`=`). Обновлять её только после повторной проверки по эталонным векторам.
2. `pxfm` заявляет правильное округление (0,5 ULP) для этих функций. Правильно округлённый результат математически единственен. Поэтому он одинаков на любой ОС и процессоре, а с лазером на любой платформе совпадает не реже, чем это возможно в принципе: каждая из системных libm на подавляющем большинстве входов даёт именно его.
3. Заявление проверено, но не доказано. Сверка с MPFR: 737 756 входов из тестов и 5,3 млн случайных (игровые диапазоны и весь диапазон `double`/`float`), сборки с FMA и без. Найдено три отклонения от C99 Annex F, все вне игровых входов. Их исправляет обёртка в `slam_osu::math`:
   - `pow(1, NaN)` и `pow(NaN, ±0)` дают NaN вместо 1;
   - `pow(x, -0.5)` без FMA даёт NaN при x > ~1e300 (переполнение разбиения Деккера). Обёртка масштабирует x точной степенью двойки, и неисправный путь не вызывается;
   - `atan2` даёт +0 вместо -0 при исчезновении порядка отрицательного результата.

   В остальном все результаты, включая субнормальные, совпали с MPFR бит в бит. Регрессию ловят тесты:
   - закоммиченные эталонные векторы (вход → биты результата по MPFR). Они покрывают все входы, где glibc округляет неправильно, и случайную выборку;
   - особые значения C99.

   Векторы получены одноразово: входы — запись всех вызовов из тестов `slam-osu`, результаты — MPFR (`mpfr_sin`, `mpfr_atan2`, `mpfr_pow` и др., округление к ближайшему, `mpfr_subnormalize` с порядками `double`). В файл попали только нормальные результаты.

   Тесты идут в CI на Linux и Windows. На Linux есть отдельный прогон `slam-osu` с `target-feature=+fma`: там `sin`, `cos`, `acos` и `pow` идут по веткам с FMA, выбранным при компиляции, — так же, как на aarch64.

   `atan2` и `atan2f` на x86_64 выбирают ветку во время выполнения (CPUID: AVX и FMA). Раннеры CI поддерживают FMA, поэтому ветку для процессоров без FMA CI не запускает. Её проверили один раз вручную: все векторы и 20 млн случайных входов дали те же биты, что ветка с FMA.
4. Прямые вызовы `f64::sin`, `f64::cos`, `f64::atan2`, `f64::acos`, `f64::powf`, `f32::atan2` и других функций системной libm в `slam-osu` запрещены линтом `clippy::disallowed_methods`. `sqrt` разрешён: IEEE 754 требует для него правильного округления.
5. Эталонные тесты лазера больше не привязаны к Linux/glibc и запускаются на всех платформах.

## Последствия
- Результат симуляции одинаков на Linux, Windows и macOS (x86_64 и aarch64) при одинаковой версии `pxfm`.
- С лазером на Linux совпадаем всегда, кроме редких входов, где glibc округляет неправильно (0,1–0,4 % вызовов). Ни один такой вход не изменил результат ни в фикстурах, ни в корпусе. С лазером на Windows и macOS совпадаем так же, как они совпадают с правильным результатом.
- `pow(x, 0.5)` теперь равен `sqrt(x)` бит в бит. Обход свёртки LLVM (`black_box`) больше не нужен: `f_pow` не интринсик.
- Новая зависимость с ~225 `unsafe` и одним автором. Риск снижается фиксацией версии и тестами векторов и особых значений.
- Кодовые пути `pxfm` с FMA и без различаются. Одинаковость результатов держится на правильном округлении. В CI проверены x86_64 без FMA и с FMA (при компиляции); ветка `atan2`/`atan2f` для процессоров без FMA проверена только вручную; на aarch64 и macOS тесты не запускаются.
- Выбор ветки `atan2`/`atan2f` кэшируется в `OnceLock`: первый вызов делает CPUID, а при гонке двух потоков за первый вызов один из них ждёт. Аллокаций нет; следующие вызовы — одна атомарная загрузка.
- Обёртка закрывает известные отклонения `pxfm` 0.1.30. При обновлении версии нужно повторить сверку с MPFR, включая особые значения и сборку с FMA.
- Новые функции (например, `exp`, `log` для модов или pp) добавлять в `slam_osu::math` по тем же правилам.

## Отвергнутые варианты
- **Системная libm с оговоркой.** Паритет с лазером на той же платформе, но реплей SLAM считается по-разному на разных ОС и даже на разных процессорах. Нарушает принцип детерминизма.
- **Крейт `libm` (порт musl/FreeBSD).** Детерминирован и сопровождается rust-lang, но не даёт правильного округления (1–2 ULP). Он расходится с glibc в 3–18 % вызовов и не совпадает ни с одной платформой лазера лучше, чем правильный результат.
- **`core-math` (CORE-MATH через C).** Правильное округление доказано, но крейт требует C-компилятора при сборке и тянет C-код в ядро.
- **`crlibm`.** GPL.
