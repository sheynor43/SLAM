# ADR-0045: Подготовка экранов в рабочих потоках, игра внутри стека экранов

- Статус: Принято
- Дата: 2026-10-17
- Дополняет [ADR-0044](0044-screen-stack.md) (не заменяет)

## Контекст
ADR-0044 требует, чтобы экран вступал в стек готовым, а тяжёлая подготовка шла в рабочих потоках, но не говорит как. С выбором карты (#95) это нужно в двух местах:
- список карт из папки `Songs`: сканирование на тысячи наборов, список меняется по мере сканирования;
- запуск игры из списка: чтение и разбор карты, скины, сэмплы, меши слайдеров, текстуры. До сих пор игра — отдельная команда `play` со своим окном, движком и аудиовыходом.

Ограничения: тик update и кадр draw не аллоцируют и не освобождают память, межпоточный обмен — через lock-free структуры (`rtrb`, тройной буфер), снапшот фиксированного размера.

## Решение
- **Готовые данные приходят по SPSC-кольцам `rtrb`**, по одному на направление. Поток update только забирает из кольца и клонирует `Arc`; построение и освобождение крупных данных — в рабочем потоке.
- **Поток библиотеки** (`slam-app`, пока список из одной папки): держит сканер `slam-library`, сортирует, строит `Arc<SongList>` (тип `slam-ui`) и параллельный массив путей `.osu` и публикует их не чаще раза в 100 мс. Каждый опубликованный `Arc` поток хранит у себя, пока `Arc::strong_count` не станет 1, и только тогда освобождает. Update, draw и тройной буфер лишь уменьшают счётчик. Тексты статуса (счётчик сканирования) форматируются тоже здесь: Fluent берёт мьютекс.
- **Поток загрузки игры** (`slam-app`): по запросу из update читает и разбирает карту, применяет моды, загружает скины и сэмплы, строит update-часть (всё для `PlaySession`, кроме трека) и draw-часть (`PlayView`, HUD, меши слайдеров), запрашивает текстуры у своего загрузчика текстур — отдельного на каждую игру. Готовое возвращается в update через кольцо. Отменённая подготовка (Back во время загрузки) отправляется обратно и освобождается в потоке загрузки.
- **Аудио — на всё приложение.** Выход, микшер и плеер музыки открываются при старте окна. Трек загружает update в общий плеер; `PlaySession` создаётся в update при вступлении экрана игры в стек — это навигация, где аллокации разрешены (ADR-0044).
- **Draw-часть игры живёт на время экрана.** Update передаёт её в draw через кольцо при push экрана игры. Draw создаёт GPU-ресурсы игры (меши, свои текстуры) в первом кадре, а когда экран игры уходит из снапшота, уничтожает их и освобождает draw-часть (возвращает в поток загрузки). Это тоже навигация.
- **Снапшот:** `PlaySnapshot` — отдельное поле снапшота оболочки (как предусмотрено ADR-0044), слой экрана игры его только помечает. Экран игры рисуется без сдвига перехода.
- Команда `play` остаётся инструментом разработчика до экрана результатов (#97).

## Последствия
- Выбор карты не замирает на большой папке; поток update не видит ни ввода-вывода, ни построения списков.
- Ресурсы каждой игры изолированы: после выхода её текстуры и меши уничтожаются целиком, утечек между играми нет. Цена — повторная загрузка общих элементов скина при каждой игре (до кеша скинов).
- Кадр, в котором экран игры вступает или уходит, может аллоцировать и загружать на GPU — один раз на навигацию.
- Окно оболочки открывает аудиовыход, даже если игрок не играет.

## Отвергнутые варианты
- **`std::sync::mpsc` в поток update**: новый механизм синхронизации без гарантий lock-free для update; `rtrb` уже используется.
- **Возврат старых списков в поток библиотеки через второе кольцо**: последнюю ссылку может держать draw или тройной буфер, а не update; удержание до единственной ссылки покрывает все потоки без лишнего канала.
- **Перезапуск движка и окна на каждую игру** (как команда `play`): мигание окна, повторная инициализация GL и аудио, переход стека невозможен.
- **Один общий загрузчик текстур на приложение**: нужен учёт и освобождение текстур каждой игры в общих атласах; отложено до кеша скинов.
