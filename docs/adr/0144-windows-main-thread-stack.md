# ADR-0144: Стек главного потока 8 МиБ на Windows

- Статус: Принято
- Дата: 2026-11-15
- Уточняет ADR-0068 (альфа-сборки) и ADR-0143 (лог и окно ошибки)

## Контекст
v0.1.1-alpha на Windows не запускается: чёрное окно, через пару секунд процесс завершается (#369). Журнал Windows показывает исключение `0xC00000FD` (переполнение стека) в `__chkstk` внутри `slam.exe`; запуск из консоли печатает `thread 'main' has overflowed its stack`. Главный поток при запуске оболочки проходит `shell::run_with` → `Engine::spawn_shared` → `snapshot::triple_buffer::<ShellSnapshot>`; их кадры — около 430, 155 и 470 КБ: снимок оболочки (`ShellSnapshot`, ~150 КБ) собирается на стеке по значению, а тройной буфер держит три копии до переноса в кучу. Вместе это больше 1 МиБ — столько стека линкер Windows (MSVC и lld-link) по умолчанию резервирует главному потоку. На Linux главный поток получает 8 МиБ, поэтому там игра запускается.

Переполнение стека не проходит через хук паники: Rust печатает строку в stderr и завершает процесс, поэтому ни записи о панике в `slam.log`, ни окна ошибки (ADR-0143) нет — лог просто обрывается.

## Решение
- `slam.exe` на Windows резервирует 8 МиБ стека главного потока, как на Linux: `build.rs` крейта `slam-app` передаёт линкеру `/STACK:8388608` (MSVC, lld-link) или `-Wl,--stack,8388608` (MinGW) только для бинарника `slam`.
- Тест на Windows читает PE-заголовок собранного `slam.exe` и проверяет `SizeOfStackReserve`.

## Последствия
- Резерв — адресное пространство, а не память: физически выделяются только тронутые страницы.
- Потоки update и draw создаются `std::thread` со своим размером стека и этим решением не меняются; большие снимки строятся на главном потоке.
- Кадры в сотни килобайт остаются; если снимки вырастут ещё в несколько раз, запас снова кончится. Уменьшать их (собирать слоты тройного буфера сразу в куче) — отдельная задача.
- Переполнение стека по-прежнему не попадает в лог как ошибка: последняя строка лога — последнее, что игра успела сделать. Причину видно в журнале Windows (Application Error, код `0xC00000FD`).

## Отвергнутые варианты
- Запускать игру в отдельном потоке с большим стеком (`std::thread::Builder::stack_size`): SDL требует, чтобы окно и события обрабатывались в главном потоке процесса.
- Только уменьшить кадры (снимки в куче): правка ядра без гарантии на будущее; лимит Windows остаётся в 8 раз меньше Linux, и следующий рост снимков снова уронит запуск только на Windows.
