# ADR-0017: Пробуждение update, свой тройной буфер, порядок событий ввода

- Статус: Принято
- Дата: 2026-10-08

## Контекст
ADR-0002 требует, чтобы update просыпался и по событию ввода, и по таймеру (до 8000 Гц), а draw брал снапшоты из тройного буфера, не дожидаясь update. Механизм пробуждения не определён. Кольцо ввода `rtrb` неблокирующее: ждать на нём потребитель не может. Крейт `triple_buffer`, названный в ARCHITECTURE §4, распространяется под MPL-2.0, которой нет в списке разрешённых лицензий. События разных устройств приходят в кольцо не строго по таймстемпам; событие может опоздать и прийти уже после того, как update выдал более новое.

## Решение
- **Тройной буфер** — свой (`slam-engine::snapshot`): три слота и один `AtomicU8` с индексом заднего слота и флагом свежести. Публикация и чтение — одна атомарная операция `swap`, без ожидания и аллокаций.
- **Пробуждение** (`slam-engine::wake`): пара `Waker`/`Parker` с атомарным состоянием «пусто / уведомлён / спит». `notify` — один `swap`, системный вызов только если поток действительно спит. Ожидание — сон до «дедлайн минус порог спина», затем активное ожидание. Сон: Linux — `futex` (`FUTEX_WAIT_BITSET`, абсолютный таймаут по `CLOCK_MONOTONIC`); Windows — auto-reset event и high-resolution waitable timer через `WaitForMultipleObjects`; прочие ОС — `thread::park_timeout`. Уведомления не копятся: несколько до ожидания — одно пробуждение.
- **Связь с вводом**: `slam-input` задаёт трейт `Notify`; `EventSink` вызывает его после каждого поставленного в кольцо события. `slam-input` от движка не зависит.
- **Порядок событий**: update забирает из кольца пачку (не больше заданного размера), сортирует её устойчивой сортировкой вставками по таймстемпу. Событие старше уже выданного в прошлом тике получает таймстемп последнего выданного (счётчик `reordered`). Update получает события в неубывающем порядке времени, в том числе между тиками.
- **Часы движка** — одна функция `slam_engine::clock::now_ns()`, общая для лимитера, update и перевода таймстемпов ввода.

## Последствия
- Задержка ввод → тик — время пробуждения потока (десятки микросекунд), а не период update.
- Свой `unsafe`-код в буфере и пробуждении; покрыт стресс-тестами, ревью ядра обязательно. Miri и loom пока не используются.
- Подъём таймстемпа опоздавшего события искажает его время на величину рассинхронизации устройств (обычно микросекунды); счётчик `reordered` показывает, как часто это происходит.
- При частоте update выше 1/порог спина (5000 Гц при 200 мкс) поток update крутится постоянно и занимает ядро.
- Реализация Windows проверяется только сборкой, пока нет Windows-окружения.

## Отвергнутые варианты
- Крейт `triple_buffer`: MPL-2.0, расширять список лицензий ради ~100 строк не стоит.
- `thread::park_timeout` на всех ОС: на Windows таймаут с точностью системного тика (~1–15.6 мс).
- Опрос кольца с фиксированной частотой: добавляет до периода задержки и тратит CPU впустую.
- `Mutex` + `Condvar`: блокировка на потоке ввода.
- Задерживать события на окно переупорядочивания: добавляет задержку каждому событию ради редких случаев.
- Передавать события как есть, не по порядку: судейство тогда должно само разбираться с порядком нажатий и отпусканий.
