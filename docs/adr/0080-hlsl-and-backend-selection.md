# ADR-0080: HLSL из `naga` с правкой сэмплеров, DXBC через `D3DCompile` при запуске, выбор бэкенда рендера один раз при старте

- Статус: Принято
- Дата: 2026-10-31
- Уточняет ADR-0019 (выход HLSL) и ADR-0024 (бэкенд D3D11, [#29](https://github.com/sheynor43/SLAM/issues/29))

## Контекст
По ADR-0019 шейдеры пишутся на WGSL и транслируются `naga` при сборке; по ADR-0024 на Windows основной бэкенд — D3D11. Для D3D11 нужен байткод DXBC (Shader Model 5.0). Его делает компилятор HLSL `fxc`/`D3DCompile`, который есть только на Windows; разработка и CI-сборка для `x86_64-pc-windows-gnu` идут на Linux.

Что выдаёт `naga` 30 для HLSL:
- Uniform-буферы и текстуры получают регистры из `binding_map` (`register(b<n>)`, `register(t<n>)`), вершинные атрибуты — семантику `LOC<location>`, обе точки входа — в одном исходнике.
- Сэмплеры выводятся всегда через кучу в стиле D3D12: `SamplerState nagaSamplerHeap[2048] : register(s0, space0)`, такой же массив для сравнивающих сэмплеров, `StructuredBuffer<uint> nagaGroup<N>SamplerIndexArray` и `static const SamplerState <имя> = nagaSamplerHeap[nagaGroup<N>SamplerIndexArray[<регистр>]];`. Отключить это нельзя. В D3D11 16 слотов сэмплеров, регистровых пространств в SM 5.0 нет — такой HLSL для D3D11 непригоден.

`slam-app` создаёт `GlDevice<SdlGlSurface>` напрямую в сценах `shell`, `play`, `bench`, `click`; `SpriteRenderer` и остальной код рендера уже обобщены по `Device`.

## Решение
- **HLSL при сборке.** `slam-shader-build` пишет для каждого шейдера один исходник HLSL с обеими точками входа. Регистры: `@group(0) @binding(n)` → `b<n>`, `@group(1) @binding(n)` → `t<n>`, `@group(2) @binding(n)` → `s<n>`, без пространств; номер регистра = слот HAL. Вершинный атрибут `@location(n)` — семантика `LOC`, индекс `n`. Имена точек входа берутся из отражения `naga`.
- **Правка сэмплеров.** После `naga` сборка заменяет объявления кучи: строки `nagaSamplerHeap`, `nagaComparisonSamplerHeap` и `nagaGroup<N>SamplerIndexArray` удаляются, `static const SamplerState <имя> = nagaSamplerHeap[...[<n>]];` превращается в `SamplerState <имя> : register(s<n>);`. Правка проверяет себя: если число заменённых объявлений не равно числу сэмплеров в модуле или после неё в тексте остались `nagaSamplerHeap`/`SamplerIndexArray`, сборка падает с сообщением о несовместимом выводе `naga`. Так обновление `naga` с другим выводом не пройдёт молча.
- **DXBC при запуске.** Бэкенд D3D11 компилирует HLSL через `D3DCompile` (`d3dcompiler_47.dll`, входит в Windows 10) при создании пайплайна: `vs_5_0` и `ps_5_0`, оптимизация уровня 3. Это время загрузки, не кадра. Кэш DXBC на диске — только если замер покажет заметное время старта.
- **Выбор бэкенда.** Сцены `slam-app` обобщаются по `D: Device` (вместе с типами поверхности). Бэкенд выбирается один раз при запуске: на Windows сначала D3D11, при ошибке создания устройства или swapchain — OpenGL 3.3 с причиной в логе; на Linux — OpenGL. Дальше работает мономорфизированный код одного бэкенда, без `match` и динамической диспетчеризации на кадре.

## Последствия
- Один источник шейдеров на GL и D3D11 сохраняется; в рантайме `naga` по-прежнему нет. Ошибки HLSL, которых не ловит `naga` (ограничения SM 5.0), видны только при создании пайплайна на Windows — их ловят GPU-тесты бэкенда в Windows CI (WARP).
- Вывод `naga` совпадает с соглашениями HAL (ADR-0019) без переворотов: матрицы в cbuffer — `row_major` с `mul(v, M)`, поэтому uniform-данные загружаются байт в байт как для GL, без транспонирования; `SV_Position` пишется без коррекции и стоит последним в выходе вершинной стадии.
- D3D11 сопоставляет выходы вершинной стадии со входами фрагментной по сигнатуре, а не по `@location`, как GL: входы `fs_main` должны быть префиксом выходов `vs_main` с теми же типами. Сейчас это так у всех шейдеров; проверка при сборке — часть бэкенда D3D11 ([#268](https://github.com/sheynor43/SLAM/issues/268)).
- В `Shader` HAL появляется `HlslShader` (исходник и имена точек входа). Таблица имён привязок для HLSL не нужна: регистр равен слоту. Бэкенд D3D11 ставит каждый uniform-буфер, текстуру и сэмплер в обе стадии.
- Правка сэмплеров зависит от формы вывода `naga`; при обновлении `naga` возможна её доработка (сборка об этом скажет).
- Время старта на Windows растёт на компиляцию 4 шейдеров `slam-render` (8 стадий) (оценка — десятки миллисекунд, замер — часть [#271](https://github.com/sheynor43/SLAM/issues/271)).
- Бинарник для Windows зависит от `d3dcompiler_47.dll`. Если её нет, D3D11 не создаётся и работает фолбэк OpenGL.
- Код сцен `slam-app` становится обобщённым; размер бинарника растёт на вторую копию кода рендера на Windows.

## Отвергнутые варианты
- **DXBC при сборке**: `fxc` есть только на Windows, сборка на Linux и кросс-проверка `x86_64-pc-windows-gnu` его не имеют. Хранить готовый DXBC в репозитории — второй источник правды, который легко забыть обновить.
- **Старая версия `naga` (без кучи сэмплеров) только для HLSL**: две версии в build-зависимостях, у старой свои ошибки и отдельное обновление.
- **SPIRV-Cross (WGSL → SPIR-V → HLSL)**: зрелый вывод SM 5.0, но C++ в сборке, в том числе при кросс-сборке для Windows.
- **HLSL вручную рядом с WGSL**: нарушает «шейдер пишется один раз» (ADR-0019).
- **Перечисление бэкендов (`enum AnyDevice`) или `dyn Device`**: проверка или косвенный вызов на каждой операции кадра; трейт с ассоциированными типами к `dyn` не приводится без переделки HAL.
