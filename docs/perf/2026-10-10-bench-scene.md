# Бенчмарк-сцена: пустой кадр и 500 спрайтов

> **Поправка.** Замеры сняты при работающей записи экрана в OBS, которая занимала очередь GPU: задержки `present`, p99 фреймтайма, перерасходы под лимитером и разброс FPS ниже — её следствие. Повторный замер без OBS и разбор — [2026-10-10-present-stalls](2026-10-10-present-stalls.md).

- Дата: 2026-10-10
- Изменение: первая бенчмарк-сцена (`slam-app bench`, [#12](https://github.com/sheynor43/SLAM/issues/12)), замера «до» нет.
- Метрики (бюджеты из ARCHITECTURE §18):
  - средний FPS без лимита на сцене «пустой кадр + 500 спрайтов» — цель ≥ 8000;
  - джиттер лимитера в реальном цикле отрисовки — p99 < 50 мкс.

## Машина
- AMD Ryzen 7 5700X (8 ядер / 16 потоков), 16 ГБ ОЗУ
- AMD Radeon RX 6700 XT, Mesa 26.2.3 (radeonsi, ACO), OpenGL 4.6 core
- Linux 7.2.8-1-cachyos, композитор niri (Wayland); X11 — через XWayland (`SDL_VIDEO_DRIVER=x11`)
- Мониторы 1920×1080 @ 180 Гц и @ 75 Гц, VRR выключен; окно 1280×720, оконный режим
- Рабочий стол, обычная фоновая нагрузка; приоритет потоков и привязка к ядрам не настраивались

## Команда
```
cargo build -p slam-app --release
target/release/slam-app bench [--seconds 10] [--warmup 1] [--sprites 500] [--hz 0] [--spin-us 200]
```
`--hz 0` — без лимита. Спрайты — квадраты 24×24 из одной страницы атласа, вращаются и движутся, позиции считаются в потоке draw по времени кадра; update-поток пустой. Первая секунда (создание GL-ресурсов, прогрев драйвера) не измеряется.

Что измеряется для каждого кадра:
- **фреймтайм** — интервал между началами соседних кадров (возвратами из `FrameLimiter::wait`);
- **draw** — от начала кадра до вызова `present`: `begin_frame`, заполнение батча, загрузка вершин, draw call;
- **present** — время внутри `present` (swap buffers);
- **опоздание лимитера** — `woke − deadline`, только для кадров, перед которыми предыдущий кадр закончил работу до их дедлайна. Если предыдущий кадр выбился за дедлайн, опоздание — это его перерасход, а не ошибка лимитера; такие кадры считаются отдельно («после перерасхода»).

## Выводы
- **Цель ≥ 8000 FPS выполнена**: X11 ~10 300 FPS стабильно, Wayland 8100–10 000 — на грани и с разбросом между запусками.
- **Джиттер лимитера в бюджете**: p99 опоздания ≤ 1 мкс на всех частотах, как и в изолированном замере ([2026-10-08](2026-10-08-frame-limiter.md)). Редкие выбросы до ~1.4 мс — вытеснение потока, как и раньше.
- **Узкое место — `present`, а не наш код.** Сборка и отрисовка 500 спрайтов одним draw call занимают ~30 мкс (p50); остальное время кадра — swap.
  1. Медиана `present` — 37–74 мкс даже на пустом кадре (на Wayland почти вдвое дороже, чем через XWayland). При 8000 FPS это 30–60% бюджета кадра.
  2. Периодические задержки `present` по ~1.5 мс, примерно 45 раз в секунду, есть и на пустом кадре, и на Wayland, и на X11 — то есть возникают в WSI Mesa / композиторе. Именно они дают p99 фреймтайма 0.7–1 мс и перерасходы под лимитером (5–13% кадров на 1000–8000 Гц пропускают свой дедлайн; на 4000 и 8000 Гц средний FPS ниже заданного).
  3. Без лимита draw на X11 изредка ждёт до ~0.6 мс (p99): драйвер тормозит CPU, когда очередь GPU заполнена (обратное давление). Под лимитером 1000 Гц draw p99 — 59 мкс.
- `glDrawElementsBaseVertex` (известная проблема батчера) в этой сцене роли не играет: один батч и один draw call на кадр. Оценивать на сценах с несколькими текстурами/режимами смешивания.
- Профилировщиком (Tracy, `perf`) не проверялось — не установлены; разбивка по времени получена встроенными замерами сцены.
